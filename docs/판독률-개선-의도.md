# 판독률 10회 측정 → 규칙 엔진 하드닝 (Codex 이월용 의도 문서)

> 대상: 다음 작업자(Codex). 브랜치 `feat/gemini-grounding-phase4b` 위에서 작업했다(Codex의 grounding 구현을 그대로 둔 채 규칙 엔진만 보강).
> 이 문서는 "왜 이렇게 고쳤는지"와 "다음에 무엇을 더 봐야 하는지"를 남긴다.

## 왜 이 작업을 했는가

Phase 4B(grounding) 완료 후, 실제 문구 10개(사기 5·정상 2·팩트체크 대상 2·애매 1)를 `/api/analyze`에 직접 넣어 **키 없이 규칙 엔진만으로 판독률**을 측정했다. AI가 꺼진 상태(`GEMINI_API_KEY` 미설정)에서도 지켜져야 할 안전망이기 때문이다. 결과:

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| 라우팅 정확도(플랜 모드 일치) | 8/10 (80%) | 10/10 (100%) |
| 고위험 사기를 danger 이상으로 표시 | 2/5 (40%) | 5/5 (100%) |
| 정상 문자 오탐(과대평가) | 0/2 | 0/2 (유지) |
| 팩트체크 라우팅 | 1/2 | 2/2 (100%) |

가장 심각했던 사례: 원격제어(팀뷰어) 탈취 시도가 **"안전(safe/0점)"** 으로 표시됐다 — 라우터는 사기로 인식(`RULE_ONLY`)했는데 점수 엔진은 몰라서 생긴 모순.

## 무엇을 고쳤는가 (근본 원인별)

### 1. 구조적 결함 — RULE_ONLY 판정과 위험 점수가 분리되어 있었다
`chooseAnalysisMode`(라우터)는 정규식으로 원격제어·인증번호 요구를 넓게 감지하는데, `calculateRisk`(점수 엔진)는 `rules.ts` 키워드 신호만 봤다. 라우터가 아는 걸 점수가 몰랐다.

**조치** — [risk.ts](../src/lib/risk.ts)의 `calculateRisk`에 세 번째 인자 `routingReasons`를 추가하고, RULE_ONLY 전용 이유 코드가 있으면 등급 하한(floor)을 적용한다:
- `remote_control_request`, `impersonation_with_money`, `coercion_with_payment_or_personal_info` → 최소 **critical**
- 그 외 RULE_ONLY 이유(`money_with_urgency`, `credential_request_with_link`, `app_install_with_sensitive_request`) → 최소 **danger**

**주의(구현 중 실제로 발생한 버그)**: 처음엔 `routingReasons.length > 0`이면 무조건 floor를 걸었는데, `AI_SUMMARY`의 `"general_explanation_needed"`도 비어있지 않은 배열이라 **정상 문자(#4·#5)까지 danger로 잘못 승격**됐다. `RULE_ONLY_REASON_CODES` 화이트리스트로 걸러서 고쳤다. **이유 코드를 라우터에 추가할 때마다 이 화이트리스트도 같이 갱신해야 한다** — 안 그러면 같은 버그가 재발한다.

### 2. 규칙 키워드가 좁고 조사·구어체에 취약했다 — [rules.ts](../src/lib/rules.ts)
- **원격제어 전용 규칙 신설**(`remote-control`, critical, category `remote`): 팀뷰어·애니데스크·퀵서포트·원격제어·원격조종·화면공유. 기존엔 규칙이 아예 없어 점수 0이었다.
- `pinfo-secrets`에 `인증번호`/`인증 번호` 추가(전에는 `인증서`만 있어 "인증번호를 입력하세요"가 안 잡혔다).
- `money-transfer`에 구어체 확장: 보내줘/보내줄/보내달라/부쳐줘/송금 좀 등("보내주세요" 존댓말만 있었다).
- **`money-account-request` 신설**(medium): 콜론 없는 평범한 "계좌번호" 요청("계좌번호 하나 남겨주시겠어요")도 최소 점수 신호로 인정 — 기존 `money-virtual`은 `"계좌번호:"` 콜론 패턴만 잡았다.
- `link-install`에 `설치하고`/`설치할` 변형 추가.

### 3. 팩트체크 라우팅 주제어가 좁았다 — [routing.ts](../src/lib/routing.ts)
`PUBLIC_TOPIC`에 건강 오정보 어휘(고혈압·당뇨·혈압·혈당·치매·면역·부작용·의사·병원·제약)를 추가하고, `CONSPIRACY_CLAIM`(쉬쉬·숨기는·비밀입니다 등 은폐 주장)을 신설해 `hasCheckablePublicClaim`이 "주제어+검증 가능한 주장" 또는 "주제어+은폐 주장" 둘 다 인정하도록 했다. (건강 완치 허위 사례가 "완치된다"는 이미 매칭됐지만 주제어에 걸리는 단어가 없어서 놓쳤었다.)
`remoteControl` 판정도 이제 `hasCategory(signals, "remote")`(새 규칙)를 우선 쓰고, 정규식은 보조로 남겨뒀다.

### 4. 회귀 테스트 신설 — [tests/goldenCases.test.ts](../tests/goldenCases.test.ts)
측정에 쓴 10개 문구를 그대로 테스트로 고정했다. `provider=null`(키 없음)로 `analyzeInput`을 직접 호출해 규칙 엔진만 검증한다. 핵심 불변식:
- RULE_ONLY 판정된 사기 조합은 danger 이상(원격제어·사칭+송금은 critical)
- 정상 문자 2건은 `signals.length === 0`이고 `safe` 유지(과탐 없음)
- 팩트체크 대상 2건은 `plannedMode === "GROUNDED_FACT_CHECK"`

## Codex가 다음에 봐야 할 것

1. **이유 코드 화이트리스트 동기화**: [routing.ts](../src/lib/routing.ts)에 새 RULE_ONLY 이유 코드를 추가하면 반드시 [risk.ts](../src/lib/risk.ts)의 `RULE_ONLY_REASON_CODES`(+필요시 `RULE_ONLY_CRITICAL_REASONS`)도 같이 갱신할 것. 안 하면 그 조합은 floor 없이 원래 점수로만 판정된다(치명적이진 않지만 조용히 새는 지점).
2. **`money-account-request`(medium) 오탐 가능성**: "계좌번호"라는 단어 자체가 안내문에도 흔히 등장할 수 있다("계좌번호를 잊어버리셨나요? 앱에서 확인하세요" 같은 정상 안내). 지금은 10개 샘플에서 오탐이 없었지만, 실사용 데이터가 쌓이면 이 규칙의 오탐률을 다시 점검할 것.
3. **팩트체크 라우팅 확장의 한계**: `PUBLIC_TOPIC`/`CONSPIRACY_CLAIM`은 이번에 관찰된 패턴 기반으로 넓혔다. 다른 유형의 허위정보(예: 재난·안보 관련 괴담)는 아직 다루지 않는다 — 실제 신고 사례가 쌓이면 주제어를 더 넓힐 것.
4. **표본 크기**: 10개는 최소 검증치다. 더 큰 라벨링 데이터셋(가능하면 실제 신고 문자 익명화 샘플)으로 판독률을 재측정하고 골든 케이스를 늘리는 것을 권장한다.
5. 이번 변경은 **규칙 엔진과 라우팅에만** 손을 댔다. Codex의 grounding/Provider 구현([provider.ts](../src/services/provider.ts), [gemini.ts](../src/services/gemini.ts), [geminiParsing.ts](../src/services/geminiParsing.ts))은 건드리지 않았다.

## 2차 검증과 문맥 하드닝 (Codex)

10개 골든 케이스 통과 뒤, 정상 보안 안내와 구어체를 포함한 추가 20문구를 키 없이 다시 측정했다. 사기 6건과 팩트체크 4건은 모두 기대대로 동작했지만, 정상 8건 중 5건이 위험 단어만 포함했다는 이유로 `danger` 또는 `critical`로 과대평가됐다.

대표 사례는 “인증번호를 알려주지 마세요”, “원격제어 앱 설치를 요구하지 않습니다”, “송금을 요구하면 신고하세요”였다. 이번 보완은 문장 전체를 무시하지 않고, 위험 단어 주변에 명확한 예방·부정 표현이 있는 경우에만 해당 신호를 제외한다. “인증번호는 알려주지 말고 아래 링크에 입력하세요”처럼 실제 요구가 뒤따르는 문장은 계속 `RULE_ONLY`로 판정하도록 회귀 테스트를 추가했다.

`money-transfer`의 “보내줘/보내줄”은 돈·금액·원·계좌로 같은 금전 문맥이 함께 있을 때만 송금 요구로 인정한다. 따라서 “계좌번호를 다시 보내줄래?”는 `caution`으로 남기되, “30만원을 이 계좌로 보내줄 수 있어?”는 기존처럼 위험 신호로 유지한다.

RULE_ONLY 이유 코드와 등급 하한은 `src/lib/routingPolicy.ts`의 단일 정책으로 옮겼다. 앞으로 라우터에 새 RULE_ONLY 이유를 추가할 때는 이 파일에서 이유 코드와 최소 등급을 함께 정의하면 된다. `riskLevel`을 floor로 올릴 때 `riskScore`도 `danger` 19점, `critical` 46점 이상으로 맞춰 결과 화면의 단계와 점수 범위가 모순되지 않게 했다.

이번 보완 후에는 기존 62개와 신규 정상 안내·우회 시도 6개를 자동 회귀로 유지한다. 여전히 실제 신고 문구의 대규모 익명 데이터셋은 없으므로, 다음 단계에서는 라벨링된 실사용 표본으로 오탐률과 미탐률을 별도로 측정해야 한다.
